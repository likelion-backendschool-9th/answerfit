# 문제은행 공통 계약

[청사진의 QB-01](README.md#7-브랜치별-todo와-구현-순서)에서 적용하는 입력·오류·회원 식별·접근 정책이다. 기존 ERD 기반 `question/entity`와 `user/entity`를 사용하며, 후속 API는 이 계약을 소비한다. 조회·저장 엔드포인트와 실제 토큰 검증은 각 담당 작업에서 연결한다.

## 입력 기준

| 입력 | 적용한 기준 | 이유 |
| --- | --- | --- |
| 질문 내용 | 양 끝 공백 제거 후 10~200 Unicode code point | 기존 프론트의 최소 길이와 이모지 글자 수 기준을 유지 |
| 검색어 | 양 끝 공백 제거 후 최대 100 code point, 생략하면 빈 문자열 | 화면 검색 입력과 서버 입력 상한 일치 |
| 신고 상세 검증 기반 | 선택 값, 최대 300 code point | 5유형 신고 API를 구현할 때 같은 검증기를 재사용 |
| 카테고리 ID | 필수 등록 요청에서는 null 금지, 제공한 ID는 양수 | ID 형식 검사와 실제 분류 조회를 분리 |
| 페이지 | 기본 1, 1 이상 | 화면과 같은 1부터 시작하는 페이지 계약 |
| 페이지 크기 | 기본 7, 1~100 | 기존 화면 크기를 유지하고 과도한 조회 크기를 제한 |
| 대분류·정렬·좋아요 필터 | 기본 `CS`, `LATEST`, `false` | 목록 기본 화면과 일치 |

입력 문자열 정리는 브라우저 `String.trim()`에 맞춰 NBSP·BOM을 포함한 양 끝 공백을 제거하고 내부 공백은 보존한다. QB-03의 [질문 목록 조회](list.md)는 검색 비교 시에만 내용과 검색어를 소문자로 바꾸고 브라우저 공백 문자를 제거한다. 저장된 원문과 응답 본문은 변경하지 않는다.

등록 요청은 `categoryId/content`를 받는다. 수정 요청은 두 필드 중 하나 이상을 받으며, null은 미전달로 취급한다. 제공된 내용은 등록과 같은 길이 기준으로 검증한다. null을 전달해 질문이나 카테고리를 지우는 기능은 없다.

Bean Validation은 후속 Controller의 `@Valid`에서 적용한다. 카테고리 ID가 실제로 존재하는지는 Repository 조회 후 확인하고, 사용자 질문의 분류가 CS인지는 `QuestionPolicy.requireCsCategory`로 검사한다. 양수 ID만으로 존재하는 분류라고 판단하지 않는다.

## 회원 식별 경계

문제은행의 기본 정책은 목록·상세를 포함한 회원 전용 접근이다. 공통 인증이 검증한 Servlet principal이 다음 정보를 `QuestionPrincipal`로 전달한다.

| 값 | 문제은행에서의 용도 |
| --- | --- |
| `userId` | 소유권, 좋아요, 신고 관계의 회원 식별 |
| `role` | 기존 `Role.USER/ADMIN` 권한 값 전달 |
| `status` | 기존 `UserStatus.ACTIVE/SUSPENDED` 접근 검사 |
| `deletedAt` | 탈퇴 계정 접근 차단 |

후속 Controller는 Servlet이 제공한 `Principal`을 `QuestionAuthentication.requireMember`에 전달하고, 검사 결과인 `QuestionMember`를 조회·변경 로직에 넘긴다. 이 회원 객체를 요청 body/query로 바인딩하지 않는다.

principal 없음·계약에 맞지 않는 principal·유효하지 않은 ID/권한/상태·탈퇴 계정은 `401 UNAUTHENTICATED`, 이용 정지는 `403 ACCESS_DENIED`다. 정상 USER와 ADMIN은 회원 접근이 가능하다. 관리자 전용 처리는 관리자 API의 별도 권한 규칙을 적용한다.

`QuestionPrincipal` 타입은 인증 처리와의 연결 계약이다. 토큰 서명·만료·발급자 검증을 수행하지 않으며, 사용자 입력 ID나 별도 헤더로 principal을 만드는 인증 우회 경로도 제공하지 않는다. 실제 Bearer 검증기가 이 계약으로 회원 정보를 전달해야 개발 모드 화면까지 연결된다.

## 질문 접근 정책

- 공개 여부는 `APPROVED`와 미삭제 상태로 판정한다. 답안 생성 대기/실패는 공개 여부와 분리해 기존 화면 동작을 유지한다.
- 인증된 본인의 USER 질문만 소유한 질문으로 판정한다. 관리자 등록 질문의 검토자 ID를 작성자 ID로 해석하지 않는다.
- 본인의 미삭제 `PENDING/REJECTED` USER 질문은 조회·수정할 수 있다. 사용자 삭제 권한에도 같은 변경 조건을 사용한다.
- 타인의 미승인 질문과 숨김·삭제 질문은 일반 질문 상세의 조회 대상이 아니다. 관리자라는 이유만으로 일반 상세에서 타인의 미승인 질문을 열어 주지 않는다.
- 신고는 공개 질문에 대해 본인 질문이 아닐 때만 가능하다.

정책은 엔티티를 변경하는 대신 기존 `Question` 상태와 출처·작성자·삭제 시각을 읽는다. 승인·반려·재제출·삭제 상태 전이는 기존 엔티티 메서드가 맡는다.

## 오류 응답과 적용 범위

문제은행 Controller에서 발생한 업무 오류와 MVC 입력 오류는 `code/message`를 반환한다. 검증 오류에는 `fieldErrors`의 `field/message`를 추가한다. 거절된 원문 입력이나 내부 예외 메시지를 응답에 포함하지 않는다.

```json
{
  "code": "INVALID_REQUEST",
  "message": "입력값을 확인해 주세요.",
  "fieldErrors": [
    {"field": "content", "message": "길이는 10~200자여야 합니다."}
  ]
}
```

업무상 404도 `QUESTION_NOT_FOUND`를 포함해 프론트가 API 미연동 오류로 오인하지 않게 한다. 입력 오류는 400, 인증 정보 오류는 401, 접근 거절은 403, 업무 상태 충돌은 409로 구분한다. 서버 반환값의 검증 실패는 500이며 입력 오류로 바꾸지 않는다.

예외 처리는 `com.likelion.answerfit.question`의 Controller에 한정한다. 다른 도메인의 오류 정책과 인증 필터의 entry point/access-denied 처리를 덮어쓰지 않는다. 인증 필터 단계의 오류는 인증 담당이 같은 응답 계약으로 연결해야 한다.

## 후속 연계 조건

- **인증/회원**: 검증된 principal adapter와 실제 토큰 처리가 필요하다. 프론트의 현재 `/api/members/me`와 WBS의 `/api/v1/users/me`, `USER/ADMIN`과 화면의 `member/admin` 변환은 해당 담당과 연결한다.
- **DB**: 현재 프로젝트의 H2 구성을 유지한다. 운영 DB·migration 방식과 담당은 별도 합의가 필요하며, 운영 테이블 생성이나 DDL 변경을 이번 작업에서 가정하지 않는다.
- **카테고리**: QB-02에서 기존 프론트의 분류를 기준으로 초기 데이터와 표시 순서를 적용했다. ID는 조회 응답으로 공유한다. [카테고리 조회](categories.md)의 초기화 정책을 따르며, 운영 migration의 복합 FK 적용은 DB 담당과 확인한다.
- **후속 변경 API**: 신고 5유형 enum 보강은 QB-09, 중복 신고와 좋아요 반복 요청의 DB 처리는 해당 API 구현 단계에 둔다.

테스트는 실제 엔티티를 이용한 공개·소유권 정책, 검증된 회원 정보의 접근 검사, 입력 경계값과 MVC 오류 응답을 확인한다. 테스트 전용 Controller는 오류 계약 검증용이며 운영용 질문 API가 아니다. 실제 로그인·회원 세션·DB 조회·관리자·AI 연계는 각 기능이 연결된 뒤 검증한다.
