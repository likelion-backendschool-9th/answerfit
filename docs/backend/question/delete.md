# 본인 미승인 질문 삭제

WBS `problem-bank-108`, [청사진의 QB-07](README.md#7-브랜치별-todo와-구현-순서)에 해당한다. 기존 [공통 인증 계약](contracts.md)과 질문 엔티티를 사용한다.

## 요청과 응답

`DELETE /api/v1/learning/questions/{questionId}`. 요청 본문은 없으며, 경로 ID는 양의 Long이다. 작성자는 검증된 인증 principal에서 가져온다. 쿼리·임의 헤더로 작성자나 관리자 권한을 바꿀 수 없다.

성공은 `204 No Content`이며 응답 본문과 Location 헤더가 없다. 삭제할 수 있는 대상은 `source=USER`, `author_id=인증 회원`, `status IN (PENDING, REJECTED)`, `deleted_at IS NULL`을 모두 만족하는 질문이다. 관리자 역할도 이 일반 사용자 API에서는 같은 조건을 따른다.

이미 삭제된 질문에 다시 DELETE하면 `404 QUESTION_NOT_FOUND`다. 삭제 시각을 갱신하거나 새 질문을 만들지 않는다. 삭제 후 본인·다른 회원·관리자 모두 일반 상세에서 404를 받으며, 수정도 404다. 공개 목록과 분류 집계에는 삭제 질문을 포함하지 않는다. 원래 미승인 질문도 공개 대상이 아니므로 이 삭제로 공개 건수는 바뀌지 않는다.

## 실패 응답

오류는 기존 `{code, message}` 형식을 사용한다.

| HTTP·code | 조건 |
| --- | --- |
| `400 INVALID_REQUEST` | 0·음수·비정수·Long 범위를 넘는 경로 ID |
| `401 UNAUTHENTICATED` | 검증된 회원 정보 없음·유효하지 않음·탈퇴 |
| `403 ACCESS_DENIED` | 이용 정지, 공개된 타인 질문 또는 관리자 출처 질문의 일반 삭제 요청 |
| `404 QUESTION_NOT_FOUND` | 없음·삭제·숨김·타인 미승인 질문 |
| `409 QUESTION_NOT_EDITABLE` | 본인의 USER 질문이 이미 승인됨 |
| `409 QUESTION_STATE_CHANGED` | 비관적 잠금 확보 실패 등 동시 변경 충돌 |

질문 조회 가능 여부, 소유권, 변경 가능한 상태 순으로 검사한다. 타인의 대기·반려 질문은 관리자 역할의 일반 요청에도 404로 처리한다. 관리자 출처 질문은 검토자 ID가 요청 회원과 같아도 본인 USER 질문이 아니다. 실패 응답에 본문·검토 사유·DB 내부 오류를 포함하지 않는다.

## 삭제와 기록 보존

`QuestionCommandController → QuestionCommandService → QuestionRepository`의 3계층을 사용한다. 쓰기 트랜잭션에서 `findForUpdateById`로 질문을 잠그고 수정과 공통인 권한 검사를 거친 뒤 기존 `Question.delete()`를 호출한다. JPA 변경 감지로 `deleted_at`을 설정하고 갱신 시각을 반영한다.

기존 엔티티의 `@SQLRestriction`은 조회 제외 규칙이며 물리 삭제를 soft delete로 바꾸는 규칙이 아니다. 따라서 `repository.delete*`를 호출하지 않는다. 질문 행과 ID·작성자·카테고리·본문·승인 상태·검토 정보·답안·힌트·생성 시각을 보존하며, 연관 키워드·신고·검토 이력을 지우지 않는다. REJECTED 삭제는 재제출이 아니므로 상태와 검토 정보를 초기화하지 않는다.

과거 면접의 `bankQuestionId`, 출제 당시 질문·힌트와 응시자의 답변·영상 참조도 유지한다. 문제은행의 삭제를 면접 기록 삭제로 전파하지 않는다. 기존 데이터에 기록이 연결된 경우도 보존하며, 미승인 질문을 새 면접에 출제하도록 허용하는 계약은 아니다.

## 관리자 승인과의 경합

[수정·재제출의 잠금 규칙](update.md#승인과-수정의-잠금-규칙)을 공유한다. 사용자 수정·삭제와 관리자 승인·반려·숨김·삭제는 쓰기 트랜잭션에서 첫 Question 읽기를 `findForUpdateById`의 `PESSIMISTIC_WRITE`로 수행하고, 잠금 획득 후 상태를 확인하며 커밋까지 잠금을 유지해야 한다.

- 관리자 승인이 먼저 잠그고 커밋하면, 대기하던 사용자 삭제는 APPROVED 상태를 읽고 409로 거절된다.
- 사용자 삭제가 먼저 잠그고 커밋하면, 대기하던 관리자 잠금 조회는 삭제된 질문을 반환하지 않으므로 승인할 수 없다.

선조회한 managed 엔티티를 잠금 쿼리가 자동 갱신한다고 가정하지 않는다. 잠금 없이 먼저 읽은 엔티티를 저장하는 관리자 경로는 이 보장의 대상이 아니다. 스키마와 `@Version` 컬럼은 변경하지 않는다.

## 검증과 연계

서비스·HTTP 테스트는 본인 PENDING/REJECTED 삭제, 관리자 역할의 동일 조건, 인증·경로 검증, 403/404/409와 거절 시 비변경을 확인한다. 실제 HTTP·H2 통합 테스트에서 물리 행과 원본 필드 보존, 삭제 후 상세·수정·재삭제 차단, 공개 목록·분류 집계 유지, 키워드·검토·신고·면접 질문 및 답변 스냅샷 보존을 검증한다.

별도 H2 DB의 독립 트랜잭션 두 개로 승인 선점·삭제 선점을 모두 검증한다. 관리자 경로는 같은 Repository 잠금과 실제 엔티티 승인 메서드로 재현한다. 실제 관리자 API와 운영 DB의 잠금 검증은 해당 담당과 연결할 때 진행한다.

실제 토큰 공급과 프론트 DELETE 연결은 후속 연계 작업에 속한다. 관리자 담당은 위 공통 잠금 규칙을 적용해야 한다.
