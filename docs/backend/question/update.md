# 본인 질문 수정과 반려 재제출

WBS `problem-bank-107`, [청사진의 QB-06](README.md#7-브랜치별-todo와-구현-순서)에 해당한다. 본인의 미삭제 USER 질문 중 PENDING/REJECTED만 수정한다. 기존 [공통 인증·입력 계약](contracts.md)과 ERD 기반 엔티티를 사용한다.

## 요청과 응답

`PATCH /api/v1/learning/questions/{questionId}`, `Content-Type: application/json`.

```json
{
  "categoryId": "2",
  "content": "프로세스와 스레드의 메모리 공유 차이는 무엇인가요?"
}
```

두 필드 중 하나 이상이 필요하다. 미제공 또는 null 필드는 기존 값을 유지하며, 제공한 카테고리는 실제 존재하는 CS 분류여야 한다. 본문은 양 끝 공백 제거 후 10~200 Unicode code point다. 빈 객체·두 필드 모두 null·허용 필드 없는 요청은 400이다. 추가 JSON 속성으로 소유권·출처·승인 상태·대분류·답안을 변경할 수 없다.

성공은 `200 application/json`이며 생성과 달리 새 ID나 Location을 발급하지 않는다.

```json
{"id":"123","status":"PENDING","canEdit":true,"canDelete":true}
```

작성자와 ID, 등록 시각은 유지한다. PENDING의 수정은 PENDING을 유지한다. REJECTED의 유효한 PATCH는 같은 ID의 재제출로 보고 PENDING으로 전환한다. 분류만 변경하거나 같은 분류 값을 다시 전달한 경우도 유효한 재제출이다.

재제출에서는 `reviewedBy/reviewedAt`을 null로 초기화한다. 과거 `QuestionModeration`은 삭제하지 않는다. 상세의 현재 반려 사유는 PENDING에서 null로 표시되며 본인 수정·삭제 권한은 유지된다. AI 생성이나 승인 요청은 실행하지 않고 공개 목록에도 추가하지 않는다.

## 권한과 실패 응답

본문의 형식 검증 후, 쓰기 트랜잭션에서 질문을 잠그고 조회·소유권·변경 상태를 확인한다. 이 검사가 끝난 뒤 제공된 카테고리를 검사하고 실제 변경을 적용한다.

| HTTP·code | 조건 |
| --- | --- |
| `400 INVALID_REQUEST` | 잘못된 경로 ID, 빈 수정 요청, 필드 형식·길이 등 검증 실패 |
| `400 INVALID_CATEGORY` | 허용된 본인 질문의 카테고리가 없거나 CS가 아님 |
| `401 UNAUTHENTICATED` | 검증된 회원 정보 없음·유효하지 않음·탈퇴 |
| `403 ACCESS_DENIED` | 이용 정지, 공개된 타인 질문 또는 관리자 출처 질문의 일반 수정 요청 |
| `404 QUESTION_NOT_FOUND` | 없음·삭제·숨김·타인 미승인 질문 |
| `409 QUESTION_NOT_EDITABLE` | 본인의 질문이 이미 승인되어 수정 불가 |
| `409 QUESTION_STATE_CHANGED` | 비관적 잠금 확보 실패 등 동시 변경 충돌 |

관리자 역할도 타인의 미승인 질문을 일반 수정 API로 변경할 수 없다. 관리자 직접 등록 질문은 검토자 ID가 현재 회원과 같아도 USER 소유 질문으로 취급하지 않는다.

소유권·상태 거절은 카테고리 존재 확인보다 먼저 처리해 비공개 정보를 노출하지 않는다. 실패 요청은 본문·카테고리·승인/검토 상태를 바꾸지 않는다. 충돌 응답은 DB 잠금 예외의 내부 메시지를 노출하지 않으며, 클라이언트는 현재 상세를 다시 확인한다.

## 승인과 수정의 잠금 규칙

`QuestionCommandController → QuestionCommandService → QuestionRepository`의 3계층을 유지한다. 서비스 쓰기 트랜잭션에서 `findForUpdateById`의 `PESSIMISTIC_WRITE`로 질문 행을 먼저 잠근다. 카테고리 outer fetch를 잠금 쿼리에 넣지 않는다. 허용된 부분 변경은 기존 `Question.update`와 JPA 변경 감지로 반영한다.

같은 질문을 승인·반려·숨김·삭제하는 관리자 쓰기도 다음 규칙을 공유해야 한다.

1. 쓰기 트랜잭션에서 해당 Question을 `findForUpdateById`로 처음 로드한다.
2. 잠금을 획득한 뒤 현재 상태를 확인하고 전이를 적용한다.
3. 트랜잭션 종료까지 잠금을 유지한다.

관리자 승인이 먼저 잠그고 커밋하면, 기다리던 사용자 수정은 승인 상태를 읽고 거절된다. 사용자 수정이 먼저 잠그면, 관리자는 수정이 커밋된 뒤 최신 본문을 읽어 승인한다. 잠금 없이 먼저 읽은 과거 엔티티를 나중에 저장하는 관리자 경로까지 보장하는 계약은 아니다.

JPA 1차 캐시의 기존 managed 엔티티를 잠금 쿼리가 자동 갱신한다고 가정하지 않는다. 같은 트랜잭션에서 선조회한 Question을 재사용하는 쓰기 흐름은 피하고, 현재 사용자 PATCH처럼 잠금 조회를 첫 Question 읽기로 둔다. 관리자 API 구현 시에도 같은 순서를 적용해야 한다. 스키마나 `@Version` 컬럼은 이 작업에서 추가하지 않는다.

## 검증과 연계

서비스 테스트는 권한·상태 거절, 부분 변경 병합, 잘못된 분류의 비변경, 반려 초기화를 확인한다. HTTP·H2 통합 테스트는 null/추가 JSON 속성 처리, ID·소유권·본문 보존, 검토 이력 유지와 재제출 후 상세를 검증한다.

실제 H2의 독립 트랜잭션 두 개로 관리자 선점·사용자 선점 양방향을 검증한다. 관리자 경로는 기존 엔티티의 승인 메서드와 같은 Repository 잠금으로 재현하며, 실제 관리자 API 연결을 대신하지 않는다. 운영 DB의 잠금 동작은 해당 DB를 정할 때 확인한다.

실제 토큰 공급과 프론트 PATCH 연결은 기존 후속 작업에서 진행한다. 관리자 담당은 같은 잠금 규칙으로 연결해야 한다.
