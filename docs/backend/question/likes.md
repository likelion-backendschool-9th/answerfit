# 문제은행 좋아요 등록과 취소

WBS `problem-bank-103`·`problem-bank-104`, [청사진의 QB-08](README.md#7-브랜치별-todo와-구현-순서)에 해당한다. 기존 [공통 인증 계약](contracts.md)과 `QuestionLike`·`QuestionLikeId`를 재사용한다. 면접 회차의 질문 좋아요는 별도 기능이다.

## 요청과 응답

| 요청 | 의미 | 성공 응답 |
| --- | --- | --- |
| `POST /api/v1/learning/questions/{questionId}/likes` | 본인 좋아요를 등록 상태로 설정 | `200`, `{"likeCount":1,"isLiked":true}` |
| `DELETE /api/v1/learning/questions/{questionId}/likes` | 본인 좋아요를 취소 상태로 설정 | `200`, `{"likeCount":0,"isLiked":false}` |

요청 본문은 없으며 경로 ID는 양의 Long이다. 회원 ID는 검증된 principal에서 가져온다. 쿼리나 별도 헤더로 다른 회원의 좋아요를 바꿀 수 없다. 응답은 envelope 없는 JSON이며 `likeCount`는 해당 질문의 전체 좋아요 수, `isLiked`는 요청 회원의 변경 후 상태다.

POST는 토글이 아니다. 이미 좋아요가 있으면 기존 행과 생성 시각을 유지하고 true를 반환한다. DELETE도 좋아요가 없으면 false를 반환한다. 반복 요청은 좋아요 중복 행이나 음수 집계를 만들지 않는다. 다른 회원의 좋아요와 본인이 다른 질문에 남긴 좋아요는 변경하지 않는다.

## 공개 조건과 오류

등록과 취소 모두 `APPROVED`이며 `deleted_at IS NULL`인 질문에만 허용한다. CS·인성, USER·ADMIN 출처를 모두 지원하고, 공개된 본인 질문도 좋아요할 수 있다. 관리자 역할도 같은 공개 조건을 따른다. 답안이 생성 중이거나 생성에 실패한 공개 질문도 대상이다.

본인만 상세 조회할 수 있는 PENDING/REJECTED 질문은 좋아요 대상이 아니다. 숨김·삭제 후에는 기존 좋아요가 있어도 이 API로 취소할 수 없다. 해당 요청은 404로 거절하며 기존 관계를 보존한다. 관리자 숨김·삭제가 기존 관계를 제거하거나 공개 건수를 증가시키지 않는다.

| HTTP·code | 조건 |
| --- | --- |
| `400 INVALID_REQUEST` | 0·음수·비정수·Long 범위를 넘는 경로 ID |
| `401 UNAUTHENTICATED` | 검증된 회원 정보 없음·유효하지 않음·탈퇴 |
| `403 ACCESS_DENIED` | 이용 정지 |
| `404 QUESTION_NOT_FOUND` | 없음·미승인·숨김·삭제 질문 |
| `409 QUESTION_STATE_CHANGED` | 비관적 잠금 확보 실패 등 동시 변경 충돌 |

오류는 `{code,message}` 형식을 사용한다. DB 잠금 내부 메시지와 비공개 질문 내용은 노출하지 않는다. 충돌 시 클라이언트는 현재 상세를 다시 확인할 수 있다.

## 동시 요청과 집계

`QuestionLikeController → QuestionLikeService → QuestionRepository/QuestionLikeRepository`의 3계층을 사용한다. 각 쓰기 트랜잭션의 첫 Question 조회를 `findForUpdateById`의 `PESSIMISTIC_WRITE`로 수행한다. 잠금 후 공개 상태를 검사하고 회원별 좋아요를 변경하며, flush 후 실제 관계 수를 집계한다. 잠금은 커밋까지 유지한다.

같은 질문의 좋아요 등록·취소는 질문 행 잠금으로 순서대로 처리한다. 동일 회원의 동시 POST는 한 행을 만들고, 서로 다른 회원의 POST는 회원별로 한 행씩 만든다. 동시 DELETE도 본인 행만 제거한다. POST와 DELETE가 겹치면 잠금 순서대로 적용하며 마지막으로 실행된 요청의 상태가 남는다. 기존 `(user_id, question_id)` 복합 PK도 중복 관계를 막는다. 별도 좋아요 캐시 카운터와 스키마 변경은 추가하지 않는다.

응답 집계는 해당 트랜잭션에서 변경 후 읽은 값이다. 응답 이후 다른 회원이 좋아요를 바꾸면 다음 조회의 건수는 달라질 수 있다. 동일 질문의 요청을 직렬화하는 방식이므로 인기 질문의 쓰기는 잠금 대기가 발생할 수 있다.

관리자 승인·숨김·삭제도 [공통 잠금·첫 조회 규칙](update.md#승인과-수정의-잠금-규칙)을 따라야 한다. 관리자가 먼저 숨김·삭제를 커밋하면 기다리던 좋아요 요청은 404로 거절되고 관계는 변경되지 않는다. 좋아요가 먼저 커밋하면 관리자는 이후 최신 질문을 잠그고 숨김·삭제할 수 있으며 기존 좋아요 관계는 남는다.

잠금 전에 읽은 managed Question이 자동 갱신된다고 가정하지 않는다. 잠금 없이 선조회한 엔티티를 저장하는 관리자 경로는 이 보장의 대상이 아니다.

## 검증과 연계

서비스와 HTTP 테스트에서 등록·취소, 반복 요청, 인증·경로 검증, 본인·타인·관리자 역할의 공개 조건과 오류를 확인한다. HTTP·H2 통합 테스트는 실제 복합 PK 행, 생성 시각 보존, 다른 회원·질문의 관계 보존, 상세 개인화, 목록의 `likedOnly`와 좋아요 정렬 반영을 검증한다.

별도 H2 DB의 독립 트랜잭션으로 동시 등록·취소, 서로 다른 회원의 집계와 관리자 숨김·삭제 경합을 검증한다. 관리자 경로는 같은 Repository 잠금과 실제 엔티티 메서드로 재현한다. 실제 관리자 API 및 운영 DB에서의 동작 확인은 해당 담당과 연결할 때 진행한다.

실제 JWT 공급은 [QB-10 공통 인증 연결](contracts.md)을 사용하고 프론트 좋아요 연결은 QB-11에서 진행한다. 관리자 담당은 같은 잠금 규칙을 적용해야 한다.
