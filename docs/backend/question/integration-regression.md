# 문제은행 통합 회귀 검증

[청사진](README.md)의 QB-12다. 프론트의 [조회](../../frontend/question/archive.md)·[변경 액션](../../frontend/question/actions.md)이 실제 HTTP 응답과 함께 동작하는지 검증하고, 외부 담당 연계가 필요한 부분을 구분한다. 검증 기록 기준일은 2026-11-26이다.

## 실행 방법과 범위

Java 21과 프론트 Node.js 실행 환경이 필요하다. `frontend/`에서 `npm ci`로 의존성을 설치한 뒤 `backend/`에서 실행한다.

```bash
./gradlew fullStackTest
```

이 명령은 임의 포트의 loopback 서버와 전용 H2 메모리 DB를 시작하고, 카테고리·공개/비공개 질문 fixture를 커밋한 뒤 프론트 Vitest를 실행한다. 서버·DB·fixture JSON·자식 프로세스는 테스트 수명 안에서 정리한다. 개발·운영 DB나 실제 계정 데이터는 사용하지 않는다. 프론트 파일 변경을 Gradle의 이전 성공 결과로 건너뛰지 않도록 이 작업은 명시 호출마다 실행한다.

`./gradlew test`와 `./gradlew build`는 이 별도 태그를 제외한다. 백엔드만 검증하는 환경에 Node.js 설치를 강제하지 않으며, 전체 연결을 확인할 때 `fullStackTest`를 추가로 실행한다. 프론트의 기본 `npm test`도 기존 단위 테스트만 실행한다. 통합 설정만 단독 실행하면 격리 서버 fixture가 없을 때 실패한다.

| 실제 실행하는 부분 | 테스트에서 제공하는 부분 |
| --- | --- |
| 프론트 카카오 시작·callback 처리, 쿠키 토큰 저장, 세션 조회, 질문 조회 adapter·서버 액션, 실제 fetch | Next 요청의 쿠키 저장소, connection·redirect·notFound·cache 함수의 테스트 환경 |
| 소셜 가입/기존 계정 조회, JWT 발급·서명 검증, DB 회원 권한 확인, Security 필터, Controller·Service·Repository·H2 | 외부 카카오 호출인 KakaoClient의 합성 계정 응답 |
| 조회/변경 API의 응답·업무 오류와 변경 후 재조회 | 승인·반려·숨김·삭제·답안 생성 상태를 기존 엔티티 메서드로 준비한 fixture |

HTTP 응답이나 내부 프론트 모듈을 고정값으로 대체하지 않는다. 반면 실제 카카오 동의 화면, Next의 브라우저 렌더링·캐시 갱신, 관리자 API 실행이나 AI 작업 실행을 이 자동 테스트가 입증하는 것은 아니다. 현재 H2 결과를 운영 DB의 잠금·유일 제약 검증으로 확대 해석하지 않는다.

구현 진입점은 [서버 fixture와 실행기](../../../backend/src/test/java/com/likelion/answerfit/question/integration/QuestionFullStackRegressionTest.java), [프론트 HTTP 회귀 테스트](../../../frontend/tests/integration/question-live.test.ts), [전용 Vitest 설정](../../../frontend/vitest.integration.config.mts)이다.

## 실제 HTTP 회귀 8개

| 흐름 | 확인한 결과 |
| --- | --- |
| 로그인 → 회원·분류·목록 | callback → JWT 쿠키 → `/members/me`와 회원 전용 질문 API. 실제 분류 ID, 공개 CS 11건/인성 2건, page=999의 마지막 페이지 보정과 4개 items |
| 등록 → 본인 상세 → 수정 → 삭제 | 생성 ID의 PENDING 상세, 타인 404/변경 거절, 분류·내용 수정, 빈 204 처리 후 이동과 삭제 후 404. 미승인 질문은 공개 집계에 포함되지 않음 |
| 반려 → 재제출 | 같은 ID로 PENDING 전환, 현재 반려 사유·검토 시각 해제, 타인에게 비공개 유지 |
| 좋아요와 다른 회원 | 반복 POST/DELETE의 최종 건수, 회원별 선택 상태, likedOnly 목록·집계 일치 |
| 신고 | 5유형 중 실제 요청에 사용한 두 유형의 변환, 빈 상세와 300개 이모지 수용, 중복·본인·미승인 신고 거절, 재조회 시 신고 표시 |
| 공개 상태·답안 상태 | 숨김·삭제 상세와 변경 404, 본인 승인 질문 수정 거절. 답안 PENDING/FAILED/DONE, 문단·키워드 순서, 중분류 없는 인성 질문 변환 |
| 유사 후보·개인 API 경계 | 실제 CS 검색 결과에서 후보 안내. 미연결 개인 API는 빈 목록으로 숨기지 않고 ApiNotConnectedError로 전달 |
| 인증 실패 | 토큰 없음·위조 시 세션 실패와 회원 전용 조회 중단 |

입력 전체 경계값·5유형·동시성·기록 보존은 기존 백엔드 테스트에서 확인한다. 위 통합 테스트는 이미 검증된 경계값을 전부 반복하기보다 실제 프론트 요청과 백엔드 응답 사이의 연결을 확인한다.

## 브라우저 직접 확인

검증한 프론트 production build를 `APP_ENV=local`로 `http://127.0.0.1:3100`에서 실행했다. 브라우저 연결 호스트는 사용할 수 없어 로컬 Chrome의 네이티브 UI로 확인했다. 푸터의 **목업 데이터 모드·회원**을 사용했으며 실제 API 브라우저 검증과 구분한다.

| URL·조건 | 관찰한 결과 |
| --- | --- |
| `/archive`, 비회원 | `/login?next=%2Farchive` 이동 |
| `/archive`, 목업 회원 | 목록·분류·페이지 표시, 등록 폼의 분류 선택과 한글 입력 |
| 등록 후 `/archive/{생성 ID}` | 승인대기 상세로 이동, 본인 수정·삭제 버튼 표시 |
| 해당 상세에서 문구 수정 | 같은 ID 상세에 수정 문구 표시 |
| `/archive`에서 URL 질문 좋아요 | 214 → 215, 선택 상태 반영. 상세 이동 후에도 215와 선택 상태 유지 |
| `/archive/url` 신고 | 빈 상세·질문 내용 오류로 신고 후 버튼이 ‘신고 접수됨’으로 비활성화 |
| `/archive/url`의 다음 질문 | `/archive/handshake`로 이동하고 다른 질문·답안 표시 |
| `/archive?page=2` | URL과 목록이 두 번째 페이지로 변경 |
| 직접 만든 승인대기 질문 삭제 | 확인 모달까지 관찰. ‘되돌릴 수 없음’ 문구로 자동 승인 검토가 제출을 차단하여 브라우저 삭제 완료는 미확인. 실제 HTTP 삭제는 위 자동 테스트로 확인 |

## S1~S12와 남은 연계

아래의 ‘자동’은 실제 HTTP 8개와 기존 백엔드·프론트 테스트를 함께 가리킨다. 목업 화면 관찰은 해당 UI 동작만 보완한다.

| 시나리오 | 확보한 증거 | 추가로 필요한 확인 |
| --- | --- | --- |
| S1 공개 조건·생성 상태 | 자동: 공개 집계, 비공개 404, 생성 중/실패/완료 변환 | 실제 관리자 상태 변경 이후 재조회 |
| S2 필터·정렬·페이지 | 자동: 조합·경계값, 실제 범위 초과 보정·likedOnly. 목업 UI: 2페이지 이동 | 실제 계정 브라우저에서 검색·필터 조합 |
| S3 본인 미승인 상세 | 자동: 두 실제 발급 토큰으로 본인 허용·타인 거절 | 실제 계정 브라우저에서 소유권 표시 |
| S4 등록·경계값 | 자동: 등록·입력 검증·권한. 목업 UI: 폼 → 생성 상세 | 실제 계정 브라우저에서 등록 |
| S5 반려 재제출 | 자동: ID 유지·검토 정보 초기화·이력 보존 | 실제 관리자 반려 API와 재제출 연결 |
| S6 변경 권한·경합 | 자동: 타인·승인 거절, 질문 잠금 경합 | 관리자 쓰기의 공통 잠금 규칙과 운영 DB 검증 |
| S7 삭제·보존 | 자동: 204 → 재조회 404·기록 보존. 목업 UI: 확인 모달 | 실제 계정 브라우저에서 삭제 후 이동 |
| S8 좋아요 | 자동: 반복·동시 요청·다른 회원 상태·집계. 목업 UI: 건수·선택 상태 갱신 | 실제 계정 브라우저에서 등록·취소 |
| S9 신고 | 자동: 5유형·길이·권한·중복·경합. 목업 UI: 접수 표시 | 관리자 신고 처리 이후에도 중복 정책 유지 |
| S10 분류·관리자·AI | 자동: 0건 분류·nullable 답안·생성 상태 fixture 조회 | 실제 승인 → 공개 → AI 성공/실패·키워드 저장 |
| S11 실제 인증 전체 흐름 | 자동: 카카오 외부 경계만 대체한 실제 JWT/HTTP 흐름. 목업 UI: 입력·이동·갱신 | 실제 카카오 계정의 동의·callback·개발 모드 전체 흐름 |
| S12 다른 화면 전체 데이터 | 자동: 개인 API 실패 노출·후보 검색. 목업 UI: 앞뒤 질문·페이지 이동 | 내 질문·좋아요·대시보드 담당 API 연계와 전체 건수 검증 |

QB-12 전체 완료 체크는 다음 조건이 준비될 때까지 보류한다. 해당 API 구현은 기존 담당 범위를 유지한다.

- [ ] 실제 카카오 설정과 계정으로 로그인부터 질문 변경까지 브라우저에서 확인한다. 설정은 [로그인 문서](../../frontend/user/login.md)를 따른다. 확인 시점에 `backend/.env`와 `frontend/.env.local`은 없었으며 실제 계정 인증은 수행하지 않았다.
- [ ] 관리자 승인·반려·숨김·삭제·신고 처리 API를 통합한 뒤 질문 API의 공통 잠금 규칙과 상태 재조회를 확인한다. 엔티티 fixture는 이 연계의 대체 증거로 사용하지 않는다.
- [ ] 실제 AI 답안 생성 작업을 연결해 PENDING → DONE/FAILED와 키워드 저장·화면 반영을 확인한다.
- [ ] 내 질문·좋아요·대시보드 담당 API를 연결한다. 현재 프론트가 쓰는 `/api/v1/questions`·`/api/v1/questions/liked-answers`는 이 백엔드에 없어 미연결 오류가 발생한다. 공개 질문 첫 페이지로 대신 채우지 않는다.

## 실행 결과

| 검사 | 결과 |
| --- | --- |
| `backend/`: `./gradlew build` | 성공, 기존 테스트 614개 통과·실패/누락 없음 |
| `backend/`: `./gradlew fullStackTest` | 성공, Java 실행기 1개 안에서 프론트 실제 HTTP 8개 통과 |
| `frontend/`: `npm run typecheck`, `npm run lint`, `npm run structure` | 성공, 구조 위반 없음 |
| `frontend/`: `npm test` | 17개 파일·343개 단위 테스트 통과 |
| `frontend/`: `npm run build` | 성공 |
| 문서·변경 파일: `git diff --check` | 통과 |

새 production 의존성·API·인증 우회 경로는 추가하지 않았다. 이 회귀 테스트는 이후 구조 변경 전후에 같은 공개 API 계약을 확인하는 기준으로 사용할 수 있다.
